CDN, Nginx & Caching

A practical study guide to how globally distributed HTTP caches route traffic, decide freshness, protect origins, and stay operationally different from multi-region application deployments.

RouteDNS and Anycast steer users to a nearby point of presence.
ProxyThe edge terminates HTTP/TLS and creates a separate upstream request.
CacheFresh responses are served locally; misses travel to the origin.
CollapseConcurrent misses share work so the origin avoids a stampede.

01 · Mental model

Start with one sentence

A CDN is a globally distributed, HTTP-aware reverse proxy with caching. It is not a new protocol and it is not merely a replicated application. It is a managed network of edge servers that can answer some requests without contacting your origin.

The useful abstraction

User → nearby edge → origin only when necessary. The edge can terminate TLS, inspect HTTP, apply policy, store responses, and open its own connection to the backend.

CDN

Global edge cache

Optimizes delivery and absorbs repeat traffic near users.

Load balancer

Backend distributor

Spreads uncached work across application replicas.

Redis

Application-side cache

Stores data near application compute, usually inside a region.

A realistic layered architectureEach layer reduces a different kind of work

02 · Request flow

What happens to one request?

Consider GET https://cdn.example.com/images/cat.jpg. The first request is usually expensive; the next one can be answered close to the user.

Miss, populate, then hitThe edge is an active HTTP participant—not a packet forwarder
1

Route to an edge

DNS may return a location-aware address; Anycast may advertise the same IP from many locations. Internet routing carries the user toward a suitable PoP.

2

Terminate and parse HTTP

The edge accepts the client TCP/TLS connection, reads the method, host, path, headers, and cookies, then computes a cache key.

3

Look up local cache state

If a matching response is fresh, the edge serves it. If absent or stale, policy decides whether to fetch, revalidate, serve stale, or bypass.

4

Open a separate upstream connection

On a miss, the proxy sends a corresponding HTTP request to the origin. This is a new connection; it is not rewriting the destination of the client’s packet stream.

03 · Nginx & reverse proxies

Nginx is software; “reverse proxy” is a role

Nginx is a high-performance web server written in C. Depending on configuration, the same program can serve files, reverse-proxy HTTP, balance traffic, terminate TLS, rate-limit clients, and cache upstream responses.

A

Web server

Browser → Nginx → files. It reads HTML, CSS, images, or downloads from the local filesystem.

B

Reverse proxy

Browser → Nginx → Spring Boot. It forwards an HTTP request and relays the backend response.

C

Load balancer

Browser → Nginx → one of many backends, selected by round-robin, least connections, hashing, or another policy.

One proxy, two transport connectionsLayer 7 proxying lets Nginx inspect and act on HTTP

nginx.conf · routing by path
server {
    listen 443 ssl;
    server_name example.com;

    location /api/ {
        proxy_pass http://spring_boot:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }

    location /images/ {
        root /var/www;
    }
}
Why Nginx scales well

A master process manages configuration and worker lifecycles. Worker processes use event-driven, non-blocking I/O (for example, Linux epoll) so they can manage many concurrent connections without dedicating one operating-system thread to each socket.

Layer 7 versus Layer 4

As an HTTP reverse proxy, Nginx works at Layer 7: it can route using paths, headers, cookies, and methods. Its stream module can also proxy TCP or UDP at Layer 4, where it handles connections without needing to understand HTTP messages.

04 · CDN implementation

A cache server is necessary, but not sufficient

One Nginx instance with proxy_cache is a caching reverse proxy. A global CDN adds routing, fleets of cache servers, failure handling, observability, configuration distribution, certificate management, and invalidation.

Inside one edge, around every edgeData plane serves traffic; control plane tells the fleet how

Data plane

The hot path: accept connections, terminate TLS, parse HTTP, compute keys, read/write cache storage, fetch from origins, and return bytes.

Control plane

The management path: configure zones and origins, distribute certificates, push rules, issue purges, monitor health, and roll out software safely.

The proxy/cache engine may be Nginx, Varnish, Apache Traffic Server, a Pingora-based stack, or custom software. The product is the complete distributed system around that engine—not the engine alone.

How users reach the right edge

DNS routing

Different answers

The authoritative DNS service can return different edge addresses based on resolver location, network, health, load, and policy. DNS caching means decisions persist for the record’s TTL.

Anycast

Same address, many places

Many PoPs announce the same IP prefix through BGP. Internet routing selects a reachable path—often nearby in network terms, though not guaranteed geographically closest.

After a request reaches a PoP, a local Layer 4 load balancer can distribute connections across the physical proxy/cache servers in that site.

nginx.conf · a compact caching edge
proxy_cache_path /var/cache/nginx
    levels=1:2
    keys_zone=edge_cache:100m
    max_size=10g
    inactive=60m
    use_temp_path=off;

upstream origin {
    server app:8080;
    keepalive 64;
}

server {
    listen 80;

    location /assets/ {
        proxy_pass http://origin;
        proxy_cache edge_cache;
        proxy_cache_key "$scheme$request_method$host$request_uri";
        proxy_cache_methods GET HEAD;
        proxy_cache_valid 200 301 302 10m;
        proxy_cache_valid 404 1m;

        # Stampede protection and resilience
        proxy_cache_lock on;
        proxy_cache_lock_timeout 5s;
        proxy_cache_lock_age 5s;
        proxy_cache_background_update on;
        proxy_cache_use_stale updating error timeout http_500 http_502 http_503 http_504;

        # Do not share authenticated responses
        proxy_cache_bypass $http_authorization;
        proxy_no_cache $http_authorization;

        add_header X-Cache-Status $upstream_cache_status always;
    }
}

Production policy must also account for cookies, Vary, authorization, private data, purge mechanisms, object-size limits, observability, HTTPS, and origin-provided cache headers.

05 · HTTP caching & freshness

A cached object is not automatically usable

The edge stores a response body plus metadata: cache key, headers, insertion time, freshness lifetime, validators, and policy state. On every request it asks, “Do I have a matching response, and may I reuse it now?”

fresh ⇔ current_age < freshness_lifetime

Freshness lab

CACHE HIT
Serve directly from the edgeThe object remains fresh for 40 seconds. The origin is not contacted.

If-None-Match: "cat-v7-a81c"

# No new body needed
HTTP/1.1 304 Not Modified

Fresh hit

Return the stored response immediately and typically increase the downstream Age value.

Stale + validator

Send If-None-Match or If-Modified-Since. A 304 refreshes metadata without retransmitting the body.

Stale without validator

Fetch a new representation. The edge may temporarily serve stale if policy permits.

Bypass / uncacheable

Forward to origin when requests are personalized, unsafe to share, explicitly private, or disallowed by policy.

Consistency is intentionally relaxed

Each edge has independent cache state. Updating the origin does not instantly update every copy. Common strategies are:

1

Short TTL

Bound staleness by letting old objects expire soon. More origin traffic, simpler operations.

2

Purge / invalidate

Send a control-plane instruction to discard or revalidate keys. Fast, but distributed propagation is not perfectly instantaneous.

3

Versioned URL

Publish cat.v8.jpg or a content hash. New content gets a new key, allowing long immutable TTLs.

Best default for static assets

Use fingerprinted filenames plus a long Cache-Control: public, max-age=31536000, immutable. Change the URL when the bytes change.

06 · CDN vs multi-region

Replicate content—or replicate the application?

A CDN is often cheaper, but cost is not the deepest distinction. The CDN replicates reusable HTTP responses on demand. Multi-region architecture replicates compute and often requires a deliberate data strategy.

Example

1 TB delivered

A 1 MB object requested one million times produces roughly 1 TB of user-facing delivery.

95% hit ratio

≈ 50 GB from origin

Only the miss traffic crosses from the origin to the CDN, reducing backend egress and request load.

Important

Still 1 TB overall

The CDN still sends the full terabyte to users. Savings come from managed edge capacity, less origin work, and avoiding full app stacks everywhere.

Two valid architecturesThe right answer depends on where business logic and mutable state must run
DimensionGlobal CDNMulti-region application
What is replicatedCacheable HTTP responses, usually on demand.Application compute, services, caches, queues, and often data.
Best forStatic assets, video, downloads, public or semi-public APIs, origin protection.Dynamic low-latency operations, regional writes, data residency, stronger regional failover.
Data consistencyPer-edge TTL, revalidation, invalidation, versioning.Database replication, conflict handling, ownership, quorum, failover.
Operational burdenMostly delegated to the provider.You operate application and data lifecycles in each region.
Cost shapeTransfer and request pricing; reduced origin egress and compute.Baseline capacity, networking, observability, and duplicated services in every region.
Cache miss latencyStill pays the trip to the origin.Can run logic locally if its dependencies are local too.
They are complements, not enemies

Large systems often use both: a CDN for globally cacheable delivery and multi-region applications for dynamic, latency-sensitive, or residency-constrained operations.

07 · Request coalescing

Deduplicate work that is happening now

Caching answers “Have we computed this before?” Request coalescing—also called request collapsing or singleflight—answers “Is someone already computing this key right now?” They solve different parts of the same stampede problem.

Many waiters, one leaderEvery caller receives the same eventual result
Java · local singleflight with CompletableFuture
final class ProductLoader {
    private final ConcurrentMap<String, CompletableFuture<Product>> inFlight =
        new ConcurrentHashMap<>();

    CompletionStage<Product> getProduct(String id) {
        Product cached = cache.getIfPresent(id);
        if (cached != null) {
            return CompletableFuture.completedFuture(cached);
        }

        CompletableFuture<Product> mine = new CompletableFuture<>();
        CompletableFuture<Product> existing = inFlight.putIfAbsent(id, mine);

        if (existing != null) {
            return existing;                    // follower
        }

        // This caller is the leader. Recheck after winning the race.
        Product secondCheck = cache.getIfPresent(id);
        if (secondCheck != null) {
            mine.complete(secondCheck);
        } else {
            database.findAsync(id).whenComplete((product, error) -> {
                if (error != null) {
                    mine.completeExceptionally(error);
                } else {
                    cache.put(id, product);
                    mine.complete(product);
                }
            });
        }

        mine.orTimeout(2, TimeUnit.SECONDS)
            .whenComplete((value, error) -> inFlight.remove(id, mine));
        return mine;
    }
}

Why putIfAbsent matters

It is atomic. Exactly one caller installs its future for a key and becomes leader. Every concurrent follower observes the installed future.

No thread per waiter required

With asynchronous I/O, waiting requests register callbacks and release execution threads. The server still retains request and continuation state.

Cleanup must be unconditional

Remove the map entry on success, error, and timeout. Otherwise one failed future can poison that key or leak memory.

Bound the blast radius

Use deadlines, waiter limits, bounded key cardinality, backpressure, metrics, and policies for whether failures should be shared.

Does this make the application stateful?

It introduces ephemeral coordination state, but the service can still be stateless in the deployment sense. Losing the map may fail or duplicate in-flight work, but it does not lose durable business data or require a user to return to the same instance.

Exampleproduct:123 → CompletableFutureShopping cart, session, order, account balance

The multi-instance limit

Ten application instances mean up to ten leaders for the same key—one per in-memory map. Global coalescing needs shared coordination, key-affinity routing, or a caching service that collapses misses. That complexity is often unnecessary: reducing 10,000 queries to 10 may already be enough.

Nginx does this at the cache layer

With proxy_cache_lock on;, one request populates a missing cache key while others wait. proxy_cache_lock_timeout limits waiting; proxy_cache_lock_age allows another upstream request when the leader appears stuck. Therefore, “one origin request” is a protection goal—not an unconditional exactly-once guarantee.

08 · Tradeoffs & failure modes

Fast paths create new responsibilities

Personalization leaks

A bad cache key can serve one user’s data to another. Include every representation-changing dimension or bypass shared caching.

Cache cardinality explosion

Cookies, query parameters, device variants, and language headers can fragment the key space and destroy hit ratio.

Stampede after expiry

Popular keys can expire simultaneously. Use coalescing, jittered TTLs, stale-while-revalidate, warming, or a cache shield.

Head-of-line dependency

All coalesced callers inherit the leader’s latency and error. A single slow fetch delays the entire waiter group.

Completion burst

One future finishing can wake thousands of responses at once. The database was protected, but CPU, sockets, and egress still see the burst.

Stale correctness

Serving stale can improve availability, but it is unsafe for some data. Apply it per resource, not as a blanket reliability switch.

A CDN helps even when it does not cache

It can still provide TLS termination, DDoS absorption, WAF policy, connection reuse, protocol optimization, global ingress, and edge compute. But it does not magically make a 500 ms uncacheable database operation compute faster.

09 · Keep this mental model

Concise recap

✓CDN: a global fleet of HTTP-aware reverse proxies and caches.
✓Nginx: concrete software that can serve, proxy, balance, and cache.
✓Routing: DNS and/or Anycast gets traffic to an edge; local balancing picks a server.
✓Freshness: headers and policy determine whether a stored response may be reused.
✓Control plane: distributes configuration; the data plane serves actual requests.
✓Multi-region: replicates compute and data strategy—not just HTTP output.
✓Singleflight: one in-flight future per key deduplicates concurrent work.
✓Statelessness: temporary coordination state does not equal durable instance affinity.
