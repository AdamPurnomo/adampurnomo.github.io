01 · Orientation

The entire receive path, on one page

For simplicity, two queues and two workers are shown. Any RX queue can feed either eligible socket; the columns are not guaranteed one-to-one mappings. RPS, offloads and other paths may change which CPU runs later processing.

Hardware bottleneck

A receive queue cannot be drained/replenished fast enough. The NIC can drop packets before the UDP socket.

Software bottleneck

A single socket receive buffer or its synchronization becomes the limit, even if multiple RX queues work.

Locality bottleneck

Threads compete for one core, share an SMT core, or move packet data across NUMA domains.

02 · Vocabulary

What is a packet, and how big is it?

The article deliberately uses tiny datagrams. Packet rate stresses per-packet handling overhead much more than sending a few large chunks of data.

The article's packet anatomy

14 BEthernet
20 BIPv4
8 BUDP
32 BApplication payload
14 + 20 + 8 + 32 = 74 bytes

IPv4 = Internet Protocol version 4; UDP = User Datagram Protocol. This count excludes the 4-byte Ethernet FCS (Frame Check Sequence), physical preamble/start delimiter, and inter-frame gap.

MTU — Maximum Transmission Unit

Typically 1,500 bytes for an ordinary Ethernet IP packet. It includes the IP header, but not the Ethernet header. With standard IPv4 + TCP (Transmission Control Protocol) headers, 1,460 bytes remain for TCP data.

MTU is a maximum, not a target. The experiment's packets are far smaller.

PPS versus bandwidth

PPS = packets per second. One million 74-byte frames corresponds to 592 megabits/s when counting only those 74 bytes. Adding Ethernet FCS, preamble and inter-frame gap raises wire occupancy (typically 784 megabits/s for these frames).

CPU pain often scales with packets, not only with total bytes.
03 · User/kernel boundary

Why sendmmsg() matters

System calls have fixed overhead. The sender batches multiple UDP datagrams into one entry into the kernel, without merging them into one network packet.

send() — one datagram per call

User program
↓ send(packet 1)
Kernel
↑ then ↓ send(packet 2)
Kernel again

1,024 UDP datagrams require 1,024 calls (assuming one send() per datagram).

sendmmsg() — many per call

User program: array of 1,024 messages
↓ one system call
Kernel processes up to 1,024 sends
↓
1,024 separate UDP datagrams

A successful call can send fewer than requested messages. recvmmsg() similarly batches receive operations.

Terminology correction: A user → kernel mode transition is not automatically a process context switch. The same software thread can make the system call and return without the scheduler switching to another thread.

Why did the article configure iptables first?

The receiver's Linux firewall rules could otherwise add filtering overhead or connection-tracking overhead to a benchmark meant to study packet reception. The first command accepts UDP port 4321; the second bypasses connection tracking for the matching traffic, but does not bypass every firewall hook.

# Commands from the original controlled benchmark
iptables -I INPUT 1 -p udp --dport 4321 -j ACCEPT
iptables -t raw -I PREROUTING 1 -p udp --dport 4321 -j NOTRACK

The receiver also configured multiple local IP addresses to make it possible to steer different flows into separate hardware RX queues. Do not casually apply these permissive firewall rules to production machines.

What does SOCK_DGRAM choose?

socket(AF_INET, SOCK_DGRAM, 0) usually creates a UDP socket on Linux. AF_INET selects the IPv4 address family; SOCK_DGRAM requests message-oriented datagram semantics; protocol 0 selects the default (UDP for this combination). SOCK_DGRAM alone is not universally UDP: Unix-domain datagram sockets also exist.

Article-style pseudocode (not directly runnable in stock Python)
fd = socket.socket(socket.AF_INET, socket.SOCK_DGRAM)
fd.bind(("0.0.0.0", 65400))
fd.connect(("192.168.254.1", 4321))
while True:
    fd.sendmmsg(["\x00" * 32] * 1024)

The article uses illustrative Python-like pseudocode. Ordinary Python socket objects do not expose sendmmsg() directly.

04 · Hardware receive path

Is an RX queue hardware or software?

Both, in a precise sense: the NIC hardware manages a receive-queue engine, while its descriptor ring and packet buffers generally live in system RAM.

Ethernet frame arrives at NICNIC = Network Interface Card
↓
NIC hardware stateChooses RX queue; manages producer/consumer positions
System RAMRing of descriptors pointing to packet buffers
↔ DMA (Direct Memory Access)
Packet buffers in RAMThe NIC writes packet bytes directly to memory, using posted descriptors
↓
Driver + NAPI polling on a CPUConsumes completed descriptors, passes packets up the stack, replenishes available buffers

Descriptor ring

A circular collection of entries describing memory buffers. It is not simply a list of UDP packet objects stored inside the network card.

D0 → buffer AD1 → buffer BD2 → buffer CD3 → buffer D

Packet drops before the application

The article's Solarflare counter rx_nodesc_drop_cnt rose at roughly 451k/s while RX queue 4 handled about 355k/s. No available receive descriptor means the NIC cannot place an incoming packet into a posted buffer.

Two distinct packet-drop locations

WhereIndicative metricWhat goes wrong
NIC / hardware queuerx_nodesc_drop_cnt (Solarflare-specific)The NIC lacks available posted RX descriptors/buffers; packet may never reach the kernel stack.
Kernel / socket receive pathnetstat -su, including RcvbufErrorsPackets reached the kernel, but delivery into the application-facing socket could not keep up. Socket queue overflow is one possible cause.

Statistics are driver/kernel specific. UDP receive error counters and their subcounters should not simply be added as independent packet counts.

Kernel work ≠ separate process. Hardware interrupts, NAPI (New API) polling, softirq (software-interrupt) processing and sometimes ksoftirqd kernel threads participate. The path is more nuanced than “a background process reads packets and sends them to the kernel.” The NIC already hands packet data to the driver/kernel through memory.
05 · Two distinct decisions

RSS chooses the RX queue. SO_REUSEPORT chooses the socket.

The most useful distinction in the article: distributing packets over NIC hardware queues does not automatically distribute them across application receive buffers.

First: RSS — Receive Side Scaling

NIC hardware hashes fields from the packet's network flow and chooses an RX queue. Packets in a stable flow generally use the same queue, helping avoid queue-induced reordering.

Cloudflare's Solarflare configuration hashed source + destination IPv4 addresses only for UDP, not the port numbers. Sending to another destination IP let it spread traffic across queues.

Second: SO_REUSEPORT

Linux can let multiple sockets bind the same UDP port and select one eligible socket for each datagram. Each socket has a separate receive buffer. This avoids the earlier single-socket contention.

In the benchmark, four workers did not receive even traffic automatically: two were idle owing to collisions in the reuse-port selection.

07 · CPU topology

One core can run two hardware threads. Why is that not always faster?

Intel Hyper-Threading (HT) is a form of SMT (Simultaneous Multithreading). A core holds two separate hardware-thread architectural states, but they share much of the execution machinery.

A core can issue/execute independent instructions from both hardware threads in overlapping clock cycles, using different execution resources. This is true concurrency, not just rapid time-slicing — but not double the physical hardware.

08 · Memory topology

NUMA = Non-Uniform Memory Access

A NUMA node is a locality domain: CPU cores plus memory that is relatively fast for those cores to access. The memory is ordinary system RAM, not a special type of RAM.

NUMA NODE 0
Physical CPU / cores 0–5
↕ fast local access
Ordinary RAM bank A
⇄
Inter-socket link
Remote access
NUMA NODE 1
Physical CPU / cores 6–11
↕ fast local access
Ordinary RAM bank B

Typical two-socket topology, not a universal rule: a socket may contain multiple NUMA nodes, and systems can expose memory-only nodes. Either CPU can generally access both memory regions through a shared address space.

Why same node?

NIC processing, packet buffers and the application can exchange data more efficiently when execution and memory are NUMA-local. Cross-node access can increase latency and consume interconnect bandwidth.

What Cloudflare measured

Receiver on another core in the RX queue's NUMA node: ~360k pps. Receiver on a different NUMA node: ~330k pps with higher variability. Later stress tests saw larger penalties.

Ideal for this benchmark: Place NIC RX-processing CPUs and application workers on separate physical cores within the same NUMA node, with local memory where practical. It's a performance choice, not a correctness requirement.

10 · Hands-on reference

Inspect, pin and verify on Linux

These commands demonstrate the mechanism. Replace interface names, interrupt numbers and chosen CPUs with values from your actual machine. Don't blindly apply benchmark tuning to a production host.

A. Discover CPU, NUMA and NIC topology

Inspection only
# Logical CPU, physical core, socket and NUMA node
lscpu -e=CPU,CORE,SOCKET,NODE
numactl --hardware

# Replace eth0 with the target interface
cat /sys/class/net/eth0/device/numa_node
ethtool -l eth0
ethtool -S eth0
ethtool -n eth0 rx-flow-hash udp4

A NIC's numa_node value of -1 means unknown/unreported; device location may not be meaningful inside some virtualized environments.

B. Check NIC receive-queue CPU mapping

# Find the relevant NIC interrupt entries
cat /proc/interrupts

# Example: examine interrupt 123 (placeholder only)
cat /proc/irq/123/smp_affinity_list
cat /proc/irq/123/effective_affinity_list

# Check Receive Packet Steering (RPS) CPU masks
cat /sys/class/net/eth0/queues/rx-0/rps_cpus

IRQ = Interrupt Request. RPS = Receive Packet Steering: software can select a different CPU for later protocol processing. An interrupt's affinity alone does not prove where all packet processing runs.

C. Illustrative CPU placement (admin privileges required for IRQ changes)

# Example only — IRQ 123 is not an actual discovered IRQ
# Tell Linux to target logical CPU 2 for that interrupt
echo 2 | sudo tee /proc/irq/123/smp_affinity_list

# Keep application on another PHYSICAL core, CPU 3
taskset -c 3 ./udpreceiver1 0.0.0.0:4321

# Alternatively: CPU + NUMA memory binding (where applicable)
numactl --physcpubind=3 --membind=0 \
  ./udpreceiver1 0.0.0.0:4321
Take care: irqbalance or the NIC driver may override/limit interrupt placement. --membind=0 is a strict allocation policy and can fail if node 0 has insufficient memory. On your one-node computer, memory binding is generally unnecessary.

D. Verify what actually happened

# Application CPU affinity — substitute real process ID
taskset -pc "$PID"
grep Cpus_allowed_list /proc/"$PID"/status

# CPU / NUMA memory placement (if numactl installed)
numastat -p "$PID"

# Runtime counters
watch -n 1 'ethtool -S eth0 | grep -i rx'
watch -n 1 'netstat -su'

# Check logical CPU sibling relationships
lscpu -e=CPU,CORE,SOCKET,NODE

Counter names and meaning vary across NIC drivers. Watch for packet drops in hardware descriptors vs drops at the socket/UDP layer.

11 · Orchestration

Does Kubernetes do this automatically?

Partially. Kubernetes can reserve CPU cores and coordinate NUMA-aware resources, but the full NIC queue → interrupt → socket path needs host and application configuration.

CPU Manager

static assigns exclusive CPUs to eligible Guaranteed containers with integer CPU requests. full-pcpus-only can allocate whole physical cores.

Topology Manager

single-numa-node coordinates topology hints from resource managers and supported device plugins.

Memory Manager

Can participate in NUMA-aware memory allocation and reservation. Requires its own enabled policy/configuration.

Illustrative kubelet policy

# Relevant kubelet configuration fields, not a full config
cpuManagerPolicy: static
cpuManagerPolicyOptions:
  full-pcpus-only: "true"
topologyManagerPolicy: single-numa-node
topologyManagerScope: pod

A workload with integer CPU request=limit and Guaranteed Quality of Service may be eligible for exclusive CPU placement. This is node-level kubelet setup, not a magic annotation you add to one Pod.

Simplified Pod resource requirements
resources:
  requests: { cpu: "4", memory: "1Gi" }
  limits:   { cpu: "4", memory: "1Gi" }

On your machine, 4 logical CPUs with the complete-physical-core policy could correspond to 2 physical cores. Kubernetes selects which IDs. Device plugins and/or specialized networking are needed for device locality; Kubernetes does not automatically tune each NIC's IRQ affinity, RSS steering, or your application's SO_REUSEPORT choices.

12 · From our conversation

Seven confusions worth remembering

Is a logical CPU a physical core?

No. A physical core can expose two logical CPUs (hardware threads) with Hyper-Threading enabled. Your core 0 contains logical CPUs 0 and 8, for example.

Can two processes literally execute simultaneously on one core?

Yes, with Simultaneous Multithreading, a core can have instructions from two hardware threads in flight together. It has multiple execution resources, not a single instruction slot. Shared resources limit gains.

Is network RX handling a separate Linux process?

Not necessarily. Kernel networking work runs in interrupt/softirq/NAPI contexts and sometimes in kernel threads. The application that calls recv() is a different software execution context, but there isn't always a standalone “NIC receiver process.”

Does taskset pin the NIC interrupt too?

No. taskset restricts where application threads may run. NIC IRQ affinity, NIC queue mapping and software Receive Packet Steering are configured separately.

Does an RX queue contain packet objects inside the NIC?

Usually not. The hardware uses a descriptor ring and packet buffers in system RAM. The NIC performs Direct Memory Access to put bytes into the buffers. The Linux driver consumes completed descriptors.

Does NUMA mean special RAM inside the CPU?

No. It's ordinarily attached system RAM (e.g., DDR modules). A NUMA node is a locality domain, not necessarily a separate chip. A remote processor can usually access the same RAM, just less efficiently.

Must every RX queue map one-to-one to a socket?

No. NIC RSS queue selection and Linux socket selection are separate routing decisions. You want an even workload distribution and favorable CPU/memory placement; a strict queue-to-socket bijection is not required.

Core principle: You need to scale both kernel-side packet reception and application-side socket consumption, while controlling CPU contention and memory locality. Optimizing only one layer can simply move the bottleneck.
13 · Reference desk

Abbreviations, fully expanded

Every term we covered, in one searchable place.

CPU — Central Processing Unit
General-purpose processor; Linux “CPU ID” usually means logical CPU.
Core — physical execution core
Contains execution resources; can expose two or more hardware threads.
SMT — Simultaneous Multithreading
Concurrent instructions from distinct hardware threads sharing one core.
HT — Hyper-Threading
Intel implementation/branding for SMT.
NUMA — Non-Uniform Memory Access
Memory access costs vary with processor-to-memory locality.
RAM — Random Access Memory
System memory holding packet buffers and application data.
NIC — Network Interface Card
Device transmitting and receiving Ethernet frames.
RX / TX — Receive / Transmit
Network-card receive and transmit directions.
RSS — Receive Side Scaling
Hardware flow-based distribution across NIC RX queues.
RPS — Receive Packet Steering
Software selection of CPUs for later kernel protocol processing.
IRQ — Interrupt Request
Hardware/software signal to CPU; affinity guides servicing CPU.
DMA — Direct Memory Access
Device accesses main memory without CPU byte-by-byte copying.
NAPI — New API
Linux networking framework for interrupt mitigation and batched polling.
UDP — User Datagram Protocol
Connectionless transport preserving datagram boundaries.
TCP — Transmission Control Protocol
Reliable ordered byte-stream transport protocol.
IP / IPv4 — Internet Protocol / version 4
Addresses and routes packets through an internetwork.
MTU — Maximum Transmission Unit
Maximum network-layer packet size for a link.
MSS — Maximum Segment Size
Maximum TCP segment data payload (excluding TCP/IP headers).
