Capstone: one inference-systems investigation

Choose the question in Month 2, produce baseline plots by Month 3, and spend Months 4–5 testing and explaining one result.

DEFAULT TRACK

Scheduling + KV-cache behavior

Under mixed short/long prompts, how does the prefill token budget affect tail time-to-first-token and decode latency as offered load increases? Characterize existing behavior, then test one bounded change against the default policy and a tuned static baseline.

ALTERNATIVE · REPLACE, DO NOT ADD

Speculative decoding

Choose this instead if algorithmic decoding interests you more. Fit a target/draft pair early, reproduce a baseline and test one narrow trade-off. Check existing adaptive methods and validate sampling assumptions. Keep the same experiment and reporting gates.

Research quality bar Predeclare a falsifiable hypothesis and constraints. Separate tuning from evaluation; control model, workload and runtime settings; report sample counts, uncertainty, failures and per-class latency. Label simulated results and validate selected trends on a real runtime. A rigorous reproduction or negative result can succeed; novelty is optional.

What not to overinvest in

  • Rust: valuable later, but defer until C++/CUDA and the research project are solid. Add it only if your target role requires it.
  • Both frameworks at once: go deep on vLLM scheduling first. Compare SGLang only when it answers the same research question; it is never a completion gate.
  • Standalone native exercises: one C++ benchmark and two CUDA kernels are enough for this plan. Skip custom containers, extra bindings and additional kernels unless the project requires them.
  • Framework deployment: don't spend weeks on serving dashboards, Kubernetes setup or API wrappers. Your goal is research-engineering competence.
  • Unnecessary GPU scale: start with small models and trace analysis on your RTX 3070. Label simulator assumptions and validate selected runtime trends; a single GPU does not establish multi-GPU training experience.
  • Forced novelty: a clean reproduction and honest failure analysis is better than a weak, unverified “new algorithm.”
